## Event Scheduling vs Fanout Analysis

`GossipStrategy.select_targets()` returns the complete list before scheduling.
`Simulator.handle_receive()` then iterates once over that list and invokes
`send_message()` for each target. Each invocation schedules one receive event.

The concrete seven-peer queue probe produced:

```text
One decision selected targets: [2, 3, 4, 5, 6, 7, 8]
Receive events scheduled from that decision: 7
```

There is no stored remainder, second forwarding round, batch-size value, or
logic equivalent to “first 6, then 1.” Seven queue entries are transport events
from one forwarding decision, not separate Gossip fanout rounds.

## Findings

Exp08 and Exp09 have no fixed fanout 3, maximum fanout 6, or other hidden
numeric cap. Both select every eligible peer in one target-selection call and
exclude the immediate sender. The earlier list was a set of peer IDs from a
five-eligible-peer diagnostic topology.
